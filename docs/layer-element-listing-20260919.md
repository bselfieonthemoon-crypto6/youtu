## 一、框选剥离（2 次图片调用）

区域 `x=0.30, y=0.43, w=0.31, h=0.25`（花布心脏）。两次独立运行（`dced6147`、`63632a0b`）结论一致：

| 检查项 | 结果 |
| --- | --- |
| 付费调用 | 各 2 次（stage-0/stage-1 归档齐全，stage-2 不存在） |
| 冻结请求 | Low/1K、`layer_backend=semantic`、1 个层名、区域一致、模型 = 报价模型 |
| 元素 | 291×285 / 283×277，30% 像素真透明，包围盒落在框内，命名「框选元素」 |
| 底图 | 元素矩形内 57 778 px 被重建；矩形外 42 px 有改动，**最大偏差 1/255**、最远 2px；**alpha 改动 = 0** |
| 画布 | 底图 + 元素共 2 个真实图片元素，`canvas_finalized_at` 有回执 |
| 计费 | 报价 0 credits、本地流水 0 条、与 `credits_cost` 一致 |

视觉检查（`artifacts/real-image-acceptance/box-split-element-*.png`、`...-background-*.png`）：
提取出的是干净透明的花布心脏；底图里心脏消失、后面被挡住的别针与纸纹被合理重建，未被框选的内容全部保留。

## 二、全部剥离（1 次视觉识别 + 3 次图片调用）

`5d62ea0c`：识别提出 4 个元素（正中偏左的碎花心形摆件 / 左下角复古女子相片 / 中部右侧黑色蕾丝蝴蝶结 /
上方中间白蝴蝶剪纸），本次只拆前 2 个。

| 检查项 | 结果 |
| --- | --- |
| 付费调用 | 识别 1 次 + 图片 3 次（stage-0/1/2 归档齐全，stage-3 不存在） |
| 元素 | 心形 608×924；相片 380×494，均有真透明像素，包围盒在图内，顺序与请求一致 |
| 元素间重复 | **共享不透明像素 = 0**（矩形框相交，但内容不重复） |
| 底图 | 元素矩形内 383 882 px 重建；矩形外 177 px，最大偏差 2/255、最远 20px；alpha 改动 = 0 |
| 画布 | 底图 + 2 个元素 = 3 个真实图片元素 |
| 计费 | 与报价一致（本地 0） |

视觉检查：相片元素干净准确；**心形元素把黑色蕾丝蝴蝶结一起带走了**，而底图里那条蝴蝶结**仍然可见**。
即生成式多元素拆分下，底图并不保证"精确移除被拆走的元素"。原因推断：生成式元素会重新排布它认为属于该
元素的部件，底图阶段的遮罩用的是生成结果的 alpha，位置与原始像素不重合，于是原物件可能被留下或被误擦。
单元素的框选剥离没有出现这个问题（框把位置钉住了）。

**结论与建议**：需要精确切割用「框选剥离」；「全部剥离」可用来快速得到分层，但**必须目视检查底图**。

## 三、供应商通道差异（未解决，需要专门跟进）

同一提示词、同一模型、同一张图，实测对比：

| 请求形状 | 结果 |
| --- | --- |
| 共享视觉适配器 `createWorkspaceVisionModel`（图片部分为 `{type:"file", data:{type:"url"}}`） | `finish_reason: "stop"`，**content 为空**，输出停在 ~599 token |
| 直接 `POST /chat/completions`（图片部分为 `image_url`） | 正常返回 `{"elements":[...]}`，reasoning ~2 162 token 后 `stop` |

因此 `layer-element-suggester` 改为**直接受限调用**（仍走 `createSafeProviderFetch`，安全边界不变），并把
`max_tokens` 提到 4 000：该上游是推理模型（`deepseek-flash`），2 000 预算会被推理吃光而返回空内容。

**未确认的影响**：沿用同一适配器的既有"图片文字识别"（`/api/images/recognize-text`）在这台网关上可能也
收不到图片，从而永远返回空列表。本次只验证到"适配器路径返回空内容"这一现象，**没有**证明 OCR 功能已坏
（OCR 的 1 000 token 预算下推理只用 114 token，行为看起来正常）。要定论需要在**含文字**的图上分别跑
适配器与原始形状对比，属于另一轮工作。
