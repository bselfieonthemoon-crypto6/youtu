# Agent 全链路审查：2026-09-11

## 结论

保留现有框架和“轻量对话 + 持久化单次执行”的方向，不恢复无人值守编排。不能宣称所有设计均已合理：确认语义与方案有效性耦合存在已实测的连续失败，需要局部修正状态边界；其余优先按 bug、可靠性与回归覆盖处理，而不是继续增加管理 Agent。

本轮为代码与官方文档审查，没有修改生产代码、数据库或调用付费模型。两名子代理均实际配置为 gpt-5.6-luna / medium；分别审查编排状态与上下文。主控复核结论、审查执行闭环并运行 37 项离线测试（worker 10、checkpoint 9、durable recovery 18），全部通过。第三个审查代理因平台线程上限未创建，其范围由主控承担。

## 官方依据与适用边界

- [Agents](https://developers.openai.com/api/docs/guides/agents)：用于审查 Agent、工具、状态与评估的组成，不是必须换框架的规定。
- [Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety)：结构化数据、权限与确认、隔离不可信输入、跟踪与评估。页面有 Agent Builder/MCP 专属建议，不能机械套用为所有本地只读工具都要用户确认。
- [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)：单次上下文需考虑输入、输出和推理；会话持久化不等于无限模型窗口。项目第三方 Chat Completions + 本地摘要不是 OpenAI 服务端 compaction。
- [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)：按真实任务分布建立持续回归，不能把测试数量或 run completed 作为业务成功标准。

## 链路判定

| 环节 | 判定 | 处理方向 |
|---|---|---|
| 用户消息、范围与权限 | 保留服务端授权、版本及所有权检查 | 不让模型自行授予权限 |
| 意图、确认与方案查询 | 有已证实的边界缺陷 | 统一确认语义；误分类不能永久隐藏旧方案 |
| 工具注册与按需加载 | 方向合理 | 保留权限校验；补第三方并行/猜测工具调用回归 |
| 写入前审核 | fail-closed 正确，可用性不足 | 解决输出截断；区分草稿与付费确认风险，不直接绕过审核 |
| 上下文与参考图 | 轻量有界方向合理 | 保留近期原文、来源关联和历史检索；不追求全历史常驻 |
| 提交、幂等、供应商快照 | 值得保留 | 防重复付费与重启重放不能仅靠聊天摘要 |
| 供应商失败处理 | 明确失败与结果未知已分开 | 未知结果不能盲目切换重试；当前仅相同上游模型备用连接 |
| 取消 | 存在代码级竞态风险 | 每个新付费阶段前重新检查取消状态 |
| 图片持久化与入画布 | 已有独立恢复闭环 | 入画布失败不能重新调用生图；继续补恢复测试 |
| 对话反馈与业务观测 | 有实测不准确反馈 | 区分本轮结束、方案存在、任务提交、图片成功和已显示 |
| 无人值守遗留 | 当前入口拒绝，仍有死代码 | 后续清理，不认定为已证实的权限绕过 |

## 优先修复

### P1：确认与方案状态级联（真实复现）

`确认，按这次修改生成。` 未被识别为 decision，SQL 方案查询把它视为新的需求分界；后续 `确认生成` 仍无法找到有效待确认方案。参考 `apps/server/src/agent/tools/image-confirmation-authorization.ts:8`、`supabase/migrations/20260910000011_image_requirement_confirmation.sql:184`。不要仅追加一条正则；需要明确“确认/更改/询问/拒绝”的状态语义，并让未发生新方案写入的失败可恢复。

### P1：审核截断与错误状态解释（真实复现）

补建方案的 reviewer 两次输出 finishReason=length，写入被拒绝。阻止未经验证写入正确，但回执使后续模型误以为原方案不存在。参考 `agent/intent-write-gate.ts:211`、`agent/image-failure-receipt.ts:183`。改进审核输出契约及预算，回执明确本次调用与既存方案的区别。详见 production-dialogue-qa-20260911.md。

### P1：取消后仍可能开始备用付费调用（代码风险，未实测竞态）

`features/jobs/job-service.ts:749` 仅将任务置 canceled；`features/jobs/executors/image-generation.ts:45` 开始时读取一次任务，`:333` 的供应商循环在下一次 generate 前未重新读取取消状态。`worker.ts:560` 等执行器返回后才收敛终态。因此若用户在首供应商运行中取消，首供应商随后明确拒绝，仍可能调用下一供应商。已有的抢占前取消测试不覆盖此窗口。应阻止取消后的新付费阶段；不能承诺第三方已接收的请求一定可撤销。

## 不应误当成必须重构的问题

- context-compaction.ts:747 的单组近期过程摘要是有意限制成本；同时合并 prior facts。这不保证所有旧细节保留，但符合轻量上下文目标。需要证明关键需求能通过摘要或检索找回，而不是改成全历史摘要。
- context-budget.ts 的 DeepSeek 预算是应用策略，不是官方容量认证。代码已区分 unverified；应验证实际网关，不能只凭名字断言可用容量，也不必为追求更大数字加重每次请求。
- demand-loaded-tools.ts 拒绝未加载 schema 的并行猜测调用是安全选择，不是已证实故障；补真实模型兼容性测试即可。
- 旧无人值守 RPC/runner 的残留是清理与纵深防御事项，当前未发现重新启用路径，不应报成现有越权漏洞。

## 验收边界

本轮 37 项为离线测试。上一轮 9 次真实用户回合只生成 2 张图，修改后确认有 2 次失败。仍须补：确认变体与失败后恢复、取消与备用调用竞态、并发确认、带图片的重启/压缩恢复、非零扣费退款、多用户隔离、真实多参考图。通过这些已明确范围后，以 bug 修复和持续回归为主，不新增复杂架构；不能声称无限轮或所有情况零错误。
