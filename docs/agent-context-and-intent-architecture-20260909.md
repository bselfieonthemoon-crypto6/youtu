# Agent 上下文与 Skills 调用边界：联合设计

日期：2026-09-09。状态：原始设计基线；后续第一版工程实施与验收见 [实施报告](./agent-context-and-intent-implementation-20260909.md)。下文的「当前情况」保留设计时的审计记录，不代表实施后的现状。

本轮依据本地源码、已安装依赖、非敏感运行记录以及 OpenAI Docs 制定。未切换模型、修改数据库、重启服务或发起付费模型调用。继续沿用现有 DeepAgents / LangGraph，不因本次需求迁移框架，不扩展企业知识库。

## 1. 结论

主 Agent 建议以**经过供应商实际确认、至少支持 128K 上下文的模型接入**作为标准配置；常规任务每次只组织约 **16K–32K** 有效输入，复杂任务约 **32K–48K**。更大的窗口用于必要的复杂任务，不应默认把整个项目、所有 Skills 和全部对话塞进去。

这组数字是 Loomic 的工程起始预算，不是 OpenAI 的强制标准，也不是当前 APIYI 模型已验证的容量。64K 接入可提供受限模式；256K 及以上可作为大批量、多画板任务的选项，不自动替用户升级模型或增加费用。

上下文大小、模型能力、信息组织是三件事。扩大窗口不能单独解决选错目标、忽略纠正、套用错误风格或工具链失败。

产品原则：**Agent 自主选择完成任务的方法；用户决定目标、限制和修改范围。用户不需要额外说“严格按照我的要求”。** 当前有效约束和真实执行状态独立保存，不能交给历史摘要、Skill 或专家建议来改写。

## 3. 上下文容量和预算

### 3.1 三个层次

1. **模型窗口**：供应商允许一次请求容纳多少输入、输出及适用的推理 token。
2. **当前工作上下文**：本次模型决策实际需要的要求、画板状态、消息、Skill 和证据。
3. **持久记录**：完整消息、附件、任务变更和工具产物；保留不代表每轮全部发送。

OpenAI Docs 明确区分上下文窗口与输出限制；上下文还可能包含推理 token。因此不能用 `maxTokens: 3000` 推断上下文只有 3000，也不能把聊天已保存等同于模型已看见。[Conversation state](https://developers.openai.com/api/docs/guides/conversation-state#managing-the-context-window)

### 3.2 128K 接入的起始配置

以下用 K ≈ 1000 tokens 表示设计预算，具体整数与计数规则由实际供应商适配。

| 预算项 | 起始值 | 说明 |
| --- | ---: | --- |
| 日常有效输入目标 | 16K–32K | 简单任务可以更小，不强制补满 |
| 复杂任务有效输入目标 | 32K–48K | 必要时允许更多有用证据 |
| 软整理阈值 | 48K | 根据任务阶段整理，目标回落到约 24K–32K；避免每轮反复摘要 |
| 发送前输入上限 | 80K | 不是默认发送量；不可超出供应商真实输入限制 |
| 生成预留 | 16K | 按供应商规则容纳输出/推理；不可超过该模型输出上限 |
| 后续工具增长余量 | 16K | 应对下一步工具返回；每次模型调用前仍重新计数 |
| 计数误差与安全余量 | 16K | 多模态或计数不确定时扩大，压缩可用输入 |

示例上界为 `80K + 16K + 16K + 16K = 128K`。通用公式：

```text
inputCeiling = min(
  verifiedProviderMaxInput,
  verifiedContextWindow - generationReserve - toolGrowthReserve - uncertaintyReserve
)
```

窗口、输入限制、输出限制要分别记录；供应商若采用不同的推理计费/窗口规则，应由适配器计算，不机械套用上式示例。48K 是软阈值，必要证据可暂时超出，80K 才是该示例的发送前上限。

生成预留必须落实到每次请求实际发送的输出/完成上限，不能只在本地扣除 16K 却仍使用供应商未限定的默认输出。当前主模型没有设置此上限，应按接入协议补齐；供应商无法可靠约束或说明推理口径时，扩大预留、降低输入上限并标注不确定性。

一个 32K 输入可初步分配为：系统与工具 6K、当前原话和有效约束 4K、近期对话 8K、历史摘要 3K、目标结构与视觉证据 5K、当前 Skills 3K、检索和工具摘要 3K。各区可借用预算；这是待真实测量校准的起点，**不允许为了凑数截掉固定文案或关键约束**。

64K 接入先按更小工作包、更多按需回读运行；256K 接入也不自动翻倍发送量。窗口是否足够，应以真实长对话评测、延迟和费用验证，不能只看宣传数字。

### 3.3 模型配置补齐

在现有 provider/model 配置及不可变运行快照中增加非敏感能力配置：

```text
contextWindowTokens / maxInputTokens / maxOutputTokens
tokenCounter: provider | tokenizer | conservative_estimate
tokenizerId / imageTokenPolicy / reasoningAccounting
profileSource / verifiedAt / profileVersion
budgetPolicyVersion / usageSupport
```

容量必须来自实际接入文档或管理员验证，不能仅根据 `gemini-*`、`deepseek-*` 等名称猜测。未知容量要显示“未验证”，由管理员配置保守运行预算；不能把预算值显示成模型真实能力。

可用时采集供应商 usage；兼容网关不支持时保持调用兼容，记录估算值与可信度，不能记成实际 0 token。文本使用匹配 tokenizer；图片按该供应商规则计入，未知则增加保守余量。usage 用于校准，不替代发送前检查。

## 4. 联合架构

```text
用户原话／当前选择／附件／最新纠正
                ↓
       意图解析 + 来源与版本记录
                ↓
上下文组装器 ← 当前画板状态、原文回查、历史摘要、按需 Skills
                ↓
         主 Agent／只读专家
                ↓
   结构化操作计划 + 目标与保留项差异
                ↓
   服务端执行校验 + 必要的真实批准状态
                ↓
      幂等工具执行 → 保存／预览验证
                ↓
   结果和证据持久化，下一轮重新读取当前状态
```

### 4.1 不随摘要失真的任务状态

扩展现有任务数据，不另造一份互相竞争的“最终需求”。统一工作包 `ContextEnvelope` 分区：

| 分区 | 来源及权限 |
| --- | --- |
| `userEvidence` | 原话、纠正原文、已确认的选择及附件引用；内容不可由模型覆盖 |
| `activeConstraints` | 有来源的有效约束，标记 `active / superseded / conflicted`；保持准确文案、目标和字段限制 |
| `observations` | 当前保存结构、图像分析、工具事实；图像分析可能有误，不等于用户授权 |
| `inferences` | 模型对用途、风格、遗漏信息的推断，注明依据和不确定性 |
| `skillSuggestions` | Skill、提示词案例和专家建议，带包版本与来源，只有方法建议权限 |
| `executionState` | 任务/设计版本、proposal/job IDs、真实状态、批准引用；从服务端重读 |
| `historySummary` | 可压缩的历史过程、已完成动作及未解决问题，带原文索引和遗漏清单 |

每条约束记录适用的任务链/target/field、来源引用、创建版本及替代关系。**同一任务纠正链内，更新仅覆盖冲突项；没有冲突的早先要求继续生效。** 同一用户稍后的澄清可解除其早先约束，但模型和 Skill 不能自行解除。

必须区分继续纠正和新任务：当前 task 行按 session 复用，无 `correctionOfRunId` 的新任务会重置 goal/corrections，不能只凭相同 taskId 把旧需求全部继承。工作包需记录纠正链起点（例如根 run ID / intent epoch）；新任务只带入确实适用且有授权来源的约束。普通聊天或未绑定设计任务使用会话工作包，不能为了保存上下文自动创建、推进设计修改任务。

原样输出文字单独存 `literalText` 与目标字段，例如名称、标题、价格和用户提供的完整节点提示词。字体/Logo 保留项绑定真实对象、字体资产或图像资产，而不仅是模糊的“不要变化”。只有确实要求原样使用的内容才视为 literal；不能把用户解释需求的一整句话误当成画面文案。

第一阶段可用 `{taskId, taskRevision, field, correctionIndex, contentHash}` 定位现有 goal/corrections，后续加入验证归属的 `sourceMessageId` 与附件引用。模型整理的 brief 仍可用于展示，但不能凭 `update_design_brief` 把推断升级为用户事实或批准。

### 4.2 历史整理

- 在**每一次模型调用前**，从当前任务版本重新注入有效约束、原样文案、目标和必要执行状态；不能只在 run 开头放一次后交给摘要处理。
- 可压缩：重复讨论、已完成步骤、冗长工具 JSON、过期提案和旧版本场景细节。当前生效约束不在摘要的可改写范围。
- 保留近期必要原文、完整 tool call/result 配对；按 token 和任务相关性裁剪，不机械保留固定 30 条。
- 摘要必须列出覆盖的 message/event 范围、来源、遗漏和生成版本。异步摘要除比对任务链、task/design revision，还要比对来源事件水位及 `contextRevision`：新消息、brief 重写等均会使工作包变更，即使 task/design revision 未变。激活摘要使用 CAS（仅当预期版本仍是当前版本才更新）；过期快照可保留审计，但不能覆盖新活动工作包。批准和 job 状态每次重读，不通过摘要恢复。
- 若完整硬约束本身过大，拆分子任务或聚焦目标；无法安全缩减时明确说明缺少哪些信息，不静默截断后执行。
- 新增只读 `read_conversation_evidence`：按受控来源 ID 回读原文及附件元数据。分页检索当前任务/会话，不默认全文加载全部历史。
- 恢复优先读取持久任务状态、有效摘要、来源索引及近期原文；原文缺失时降低信心并请求关键澄清，不能用摘要“补写”原话或批准。
- 大型工具输出存引用、hash 和相关摘录；原始图片存资产引用，避免把 base64 当普通文本无限留在历史。
- 使用一个明确的摘要/预算控制入口，显式配置或接管现有默认 middleware，避免框架摘要和应用摘要分别裁剪而相互破坏。
- 最终发送检查须发生在有效约束重新注入、框架系统指令追加、工具 schema 确定及摘要替换之后；迁移时兼容或清理既有 `_summarizationEvent` 等截止点状态，不能沿用旧截止点误裁剪新的工作包。
- 摘要模型自身也有输入/输出预算。历史过大时按来源区间分块整理后合并，并保留来源索引；摘要调用不递归触发同一整理入口。失败时保留原记录和有效任务状态，不能以空摘要覆盖。

OpenAI 的 Responses API 提供服务端/独立 compaction，但其压缩项是专用的不透明状态。我们目前采用 OpenAI-compatible Chat Completions，不能直接假设 APIYI 接入支持该协议。本方案首先做应用层状态与预算；只有实际接入支持时才增加协议适配。[Compaction](https://developers.openai.com/api/docs/guides/compaction)

## 5. Agent / Skills 的统一边界

在平台权限和安全规则内，当前用户目标与有效约束决定执行范围。系统可以自主选工具、拆步骤、调用相关 Skill、做必要验证；不能自主改变用户要交付什么。

| 用户场景 | 可自主完成 | 不应擅自做 |
| --- | --- | --- |
| 在生图节点输入完整提示词并生成 | 使用原文和用户选定参数完成生成 | 自动套案例风格或改写原文；“优化提示词”应是单独可见操作 |
| “帮我做一张咖啡新品宣传图” | 读取相关 Skill，补充合理版式、留白等开放部分 | 虚构产品价格、活动期限、品牌或未经确认的承诺 |
| “把这张 Logo 的黑底改绿色” | 锁定附件/选中 Logo，变更其背景 | 修改旁边画板背景、改比例、重设计 Logo |
| “标题改成夏日上新” | 精确替换目标文字并保留其余属性 | 顺便换字体、配色、位置或整张图重生成 |
| “做得更高级一些” | 上下文已要求修改时，在目标和保留项内自主改善；咨询语境则给出建议 | 把审美偏好当成可以重做所有内容的授权 |
| 过程中纠正“不要红色，改蓝色” | 更新颜色并让旧方案失效 | 清掉此前仍有效的文字、比例和字体要求 |

### 5.1 调用前决定，调用后检查

1. **理解任务**：结合原话、对话、选择和附件判断目标；“没说严格执行”不等于可自由改需求。区分新创作、局部编辑、建议咨询、节点原文执行。
2. **划定开放部分**：已有设计局部编辑默认保留未要求变化的部分；新创作可在未限定部分发挥。允许已授权范围内必要、低风险且可逆的实现细节，不机械要求用户指定每一项；“可逆”本身不是扩大修改范围的授权。
3. **决定是否读取 Skill**：相关能力有助于实现目标才调用，不为展示流程强制调用。精确改字、改颜色等可以直接用确定性工具；复杂创作允许多个相关 Skill 分工。
4. **识别实质偏离**：改变目标图、准确文案、品牌、指定风格/字体、输出数量/比例、预算、数据外发范围或破坏性操作，要有相应授权。关键歧义问一个短问题；普通留白和非关键排版不应反复打断。
5. **生成受控操作计划**：包含目标 IDs、前置版本、拟改字段、必须保留字段、输出设置、预计模型/费用与依据。计划并非自动批准。
6. **服务端校验**：复用已有目标/版本检查，增加可确定的字段白名单及准确值对比；若不能用结构化编辑保证字体/Logo 保留，不静默换成生成式重绘并声称无损。
7. **检查真实结果**：确定性文本/字段校验配合必要视觉检查。语义或视觉模型只能补充检查，不能充当权限凭证，也不能保证生成模型零偏差。

现有 `needsProfessionalSkill()` 对生成/模板路径以及不少编辑强制要求读取专业 Skill，需改成按任务意图和所需能力判断；同时统一主提示词、任务提示词、Skill 工具和专家提示词，避免只改一段 prompt 却留下矛盾的强制流程。

OpenAI Docs 的相关指导是结合用户指令与先前上下文理解意图，在隐含授权范围内主动推进，并明确用户指令优先于 Skill 指南。这支持上述原则，但本项目的字段校验、费用策略和预算数字属于产品设计，不应称为 OpenAI 强制要求。[Model guidance](https://developers.openai.com/api/docs/guides/latest-model#initiative-and-follow-through)

### 5.2 确认、纠正与并发

- 生图继续核对现有 `image_generation_proposals` 的冻结 input、status、approved_cost、origin_run_id 等；摘要中的“用户同意了”不是批准凭证。`fast/thinking` 是执行模式，不是授权等级。
- 用户在执行中纠正后提升任务版本，旧 proposal、专家结论和迟到结果不得套用到新要求。已经提交的供应商请求不保证可撤销费用；完成结果应明确归属旧任务，不覆盖当前设计。
- 修改动作前和提交保存时都校验目标/版本，保留已有数据库原子保护。模型调用重试不能重复付费生成；复用幂等 job/proposal，不重放所有副作用工具。
- 破坏性确认当前部分依赖进程内状态；服务重启不能凭历史摘要恢复批准。后续若持久化确认，应保留过期时间、动作 hash、目标版本和主体授权。
- 用户看到简洁的“正在修改什么 / 保留什么”和必要的差异预览，可随时纠正；不展示内部思维链，只展示公开计划、依据和实际工具状态。

## 6. Skills、提示词库与子 Agent 如何节省上下文

- 继续保留 Skills 目录检索和按需正文读取；完整读取被选 Skill 及必要引用，不能只截一半指令假称已加载。极大 Skill 应拆分资源或预先整理入口，不靠运行时盲截断。
- 同一轮按内容 hash 避免重复注入同一份正文；历史 Skill 停用后不再恢复为当前可用权限。源内容、模板和参考资料中的指令按来源隔离，不能覆盖平台政策或用户目标。
- 提示词库按需求检索少量候选，建议首批 5–8 条；供用户浏览的图片按需加载，模型只看与当前选择相关的少量图片。图片加载与模型视觉 token 是两套预算，不能用“只存 URL”推断没有视觉成本。
- 选择案例意味着允许参考与本次意图相关的内容，不自动复制案例品牌、价格和所有风格约束；逐字节点模式与用户明确选择“套用模板/优化”区别处理。
- 只读专家拿到的是同一版本的目标、约束和相关证据投影，不复制全部父会话。建议普通专家输入约 8K–16K，当前 3000-token 输出上限可保留并实测；复杂视觉审查按实际预算申请更多。
- 专家仍不拥有设计写入/付费生成权限，其建议经主 Agent 当前约束校验后才可能执行。当前字符截断和 120 对象上限可保留为大小保护，但不能替代相关性选择、token 预算和明确遗漏说明。

## 7. 持久化与多用户边界

优先复用 `agent_design_tasks`、`agent_design_task_runs`、聊天和资产表，新增服务端专用 `agent_run_context_snapshots` 保存版本化工作包、摘要索引、公开计划、预算及实际 usage/估算来源。当前 brief 更新也应进入可追踪版本，便于复现某次操作实际依据。

原消息、附件、工具产物仍保留在原存储，不将所有内容复制到每份 snapshot。摘要可复用，但缓存键至少包含 workspace、user、session、任务链、task revision、context revision、模型/预算版本，并记录来源事件水位；资产分析缓存还需要 asset 内容 hash 与分析模型版本。

读取前重新校验当前成员资格和任务访问权，不能只靠缓存键或 `assertCurrentRun`。现有聊天的工作区权限与 task 的会话创建者权限并不完全相同，新回查接口应遵循更具体的任务授权。撤权后不能继续从缓存、摘要或旧签名引用读取内容。

保留/删除策略与项目现有规则一致：删除来源时使相关摘要、缓存和索引失效，不能把“长期记忆”做成绕过删除的永久副本。日志只记录必要计数、引用、版本和公开状态，不记录凭据或内部思维链。

这些属于会话和任务工作记忆。企业文档知识库、跨项目个人偏好和向量检索是独立产品需求，本次不捆绑建设；以后添加也必须显式作用域和访问控制。

## 8. 实施顺序与验收

### 阶段 A：可靠的输入与意图底座

补模型 profile/预算观测、来源类型、当前有效约束和每次调用前的重新注入；保留既有数据库写入保护。先对未知模型显式标注能力未验证，并在无副作用测试中验证预算适配，不能先盲目增大阈值。

主要位置：`provider-config-contracts.ts`、provider snapshots、`workspace-chat-model.ts`、`deep-agent.ts`、`runtime.ts`、`agent-task-service.ts`、共享 task 契约。

### 阶段 B：统一自动调用边界

主 Agent、Skills、节点原文入口和专家共用意图策略；调整强制 Skill 条件；增加明确局部编辑的字段限制、准确文案校验、版本化差异与真实确认校验。

主要位置：`design-task-tools.ts`、`workspace-skill-tools.ts`、`loomic-main.ts`、`design-delegation-tools.ts`、图像 proposal 工具及节点生成入口。数据库新增迁移，不原地重写已应用迁移。

### 阶段 C：持久化整理与原文回读

接管摘要入口、保存摘要来源/版本、增加回查工具及恢复机制。统一预算入口覆盖主 Agent、专家、独立视觉预处理、视觉核验和摘要模型，补图片计数、上下文超限映射及幂等恢复。现有视觉预处理和默认摘要会直接调用 `model.invoke`，仅加主 Agent middleware 不足以覆盖，必须逐调用入口接线并测试。

### 阶段 D：长对话和真实设计验收

先离线合成测试和无网络模型回归，再在测试项目中做明确预算范围内的真实文本/图像验收。不得用用户正在编辑的原画板做破坏性实验。

| 场景 | 必须验证的结果 |
| --- | --- |
| 100+ 轮中文对话、多次整理 | 原始标题、指定字体、比例、禁止事项仍准确；相同有效约束 hash 不被摘要改写 |
| 最新纠正与旧要求并存 | 只替代冲突字段，其余保留；可回查对应原话 |
| 同会话新任务或普通咨询 | 不继承旧任务的无关限制；咨询不因构造工作包触发设计写入 |
| “只改标题”，未说“严格” | 文本变化，字体/颜色/位置/其他对象保持；违规命令被服务端阻止 |
| 节点完整提示词 | 最终提交原文一致；未点击优化时不套案例或隐式风格 |
| Skill/案例含相反指令 | 不获得额外修改权限；明确冲突时遵守用户要求 |
| 窗口切换、巨型工具结果、图片输入 | 调用前预算检查生效；不把图片计作 0；硬约束不被截断 |
| checkpoint 缺失、服务重启 | 从持久记录恢复意图和真实状态；缺失批准不变成已批准 |
| 摘要期间用户纠正 | 旧摘要、旧专家结论和迟到任务不能覆盖新版本 |
| task/design revision 未变但新增消息或重写 brief | 来源水位/context revision 与 CAS 拒绝过期摘要覆盖；真实批准和 job 状态仍重新读取 |
| 同时抠图/拖动待生成节点 | job/node ID 与当前节点位置正确对应；上下文重试不重复生成 |
| 跨租户、换用户、成员撤权 | 原文、摘要、缓存、附件和专家上下文均不可越权读取 |
| 保存与画布预览 | 真正保存版本与显示结果一致；不能只因模型说完成便报告完成 |

确定性约束和权限测试要求全部通过；语义意图、视觉质量、延迟和费用使用固定样本集与人工复核报告通过率，不承诺“未来所有情况 100% 不失败”。记录每轮估算/实际输入输出 token、摘要次数、召回来源、Skill 使用、超限错误、阻止的越界操作及纠正后恢复情况。

本次交付是上述设计与静态核实结果。运行实现、性能收益及长对话测试数据须在后续阶段分别验收，不能把方案标注为已上线。
