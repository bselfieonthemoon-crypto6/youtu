# 并行抠图节点位置与错误状态修复

## 实际原因

用户任务 5e479f83-b38c-48de-a36d-8594f39c2dde 和 8c399717-4b06-4161-834a-f7b89d569d9a 均 succeeded，分别对应两个点击。第二个旧占位节点 sc8e5lw5ldh9gs18vx5o 保存了拖动坐标，但落图使用 target.placement 的提交时坐标，并创建了不同 ID 的图片。前端一次任务查询失败将占位标记 error，较高元素 version 又使服务器删除标记被旧占位状态覆盖。

## 修改

- image-replacement 严格通过 placeholder ID + jobId 匹配，在原节点 ID 上替换为图片，保留最新坐标、尺寸、旋转、分组和框架关系。
- 已完成的同任务节点再次落图直接返回原节点，不删除、不新增；保留用户删除状态。
- shared 层 mergeCompletedImageReplacement 在前后端统一合并：完成图片内容不可被旧占位覆盖，但允许较新的并发拖动或删除继续生效。
- 查询异常继续轮询同一任务，只有服务端确认终态失败才显示生成失败；前端不再在成功刷新前主动删除占位。
- 保留原图、正常模型调用策略和两个独立请求，不通过合并任务掩盖故障。

## 当前数据处理

第二张结果图在修复期间被用户再次独立移动。repair-moved-matting-result.ts 检测后保留该新位置，仅将已成功任务残留的错误占位节点标记删除。两张结果均保留，无重新生图，无额外 API 调用。此占位移除是画布删除标记，不涉及物理删除资产。

## 验证

- 后端：21 项测试通过，含并行、移动、逆序完成、幂等重试、过期保存。
- 前端：18 项测试通过，含查询失败恢复、两个任务状态隔离、并发坐标合并。
- shared 构建与后端 TypeScript 检查通过。
- 真实 Chromium 回归 matting-placeholder-move.spec.ts 通过（9.6 秒）。独立画布 616a86ae-b231-42f8-9546-567f25c80b92，鼠标把第二个节点 y=350 拖至 y=70；模拟任务状态接口一次 503，使用真实存储和落图写入，倒序完成并重放落图，刷新后两张结果均保留正确位置且没有错误占位。提供商输出复用先前测试资产，本次没有调用付费 API。
